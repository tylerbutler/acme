# M4: thin template and approved init

**Status: proposed milestone plan, not implementation approval.**

## Goal and basis

Take a new project's brief to one reviewed init PR through a thin template,
an interview skill and deterministic `acme init`. Follow the
[roadmap](0001-bootstrap.md#next-milestones),
[factory boundaries](../adr/0001-factory-boundaries.md) and
[proposed M3 contract](https://github.com/tylerbutler/acme/pull/30).
Reconcile this plan with the completed M2/M3 interfaces before coding.

## Contract

- Ship a separate thin template with `factory/brief.md`, an approved-config
  stub, init-interview/spec-writer skills, an agent map and docs skeletons.
  Pin an actual released acme version and its compatible schema. Do not copy
  the CLI source, module implementation or pre-enabled workflows into it.
- Start with a supported Rust/CLI baseline. Required project inputs, such as
  Cargo files and configured CI commands, must exist or fail preflight with
  clear guidance. Do not copy acme-specific Python scripts into every project.
  Unavailable profile modules stay off; do not advertise a complete CLI
  profile before its later gates exist.
- The interview skill reads the brief and existing project facts, asks only
  unresolved questions, and proposes config. Capture repository identity,
  supported profile/languages, L3 autonomy, path risks, engines and cost limits.
  Ask about secret names and requirements, never secret values. Missing
  answers must not silently become permission for paid work or remote writes.
- A human reviews the complete config and diff before generation. The binary
  does not call an LLM, infer consent from prose, or launch the interview.
  Define the exact approval hand-off before implementation.
- `acme init` consumes approved config and reuses M1 validation and M3
  planning, rendering and ownership checks. Reject unsupported pins, schemas,
  dependencies and file conflicts before mutation. Preserve the brief,
  authored instructions, specs and project source. Re-running init must not
  overwrite a configured project; direct it to the safe sync path.
- Prepare one reviewable init change set with config, supported generated
  files, ownership bookkeeping and useful next steps. Document explicit
  branch/PR creation; never merge or provision merely because init succeeded.
- Keep local generation separate from repository administration. Supported
  label/ruleset provisioning requires a separately approved M2 repair plan.
  No workflow activation, secret upload, private-repo creation or paid test
  follows implicitly. Agent modules remain off until M5 and owner approval.

## Acceptance scenarios

1. A fresh copy of the pinned template and a minimal supported Rust project
   can complete the interview, config review and deterministic init without
   hand-editing generated files. The resulting init PR passes required checks.
2. The same approved inputs produce the same generated bytes. Missing
   prerequisites, unsupported profile options, incompatible pins and edited
   or conflicting files fail explicitly and preserve user content.
3. Cancellation or missing config approval causes no generation, remote
   provisioning, workflow activation, secret access or paid inference by the
   binary. Automated tests use local fixtures and fake remote state.
4. A spec-writer skill can use the preserved brief to propose a small feature
   spec and backlog; only the owner can approve a build with the ready label.
5. With prerequisites available, record an owner-approved sample run from
   brief to human-merged init PR, targeting under 30 minutes of wall time.
   Record waits and failures honestly; a successful render alone is not this
   exit check. The sample run and new repositories need separate permission.

## Dependencies and decisions before implementation

M3 version compatibility and owner adoption must be complete, including
[tylerbutler/acme#26](https://github.com/tylerbutler/acme/issues/26).
Do not substitute a pretend release pin for the manual stage0 release.

Before opening build slices, decide template owner/name/visibility, release
and schema compatibility, the config-approval hand-off and the initial
supported preset. Use the finished CLI interfaces, not guessed flags.

## Non-goals and approval

No actual template/sample repository creation in this planning PR, broad
language presets, rendered agent workflows, holdout provisioning, automatic
upgrades, auto-merge or L4 autonomy. Existing acme settings stay unchanged.

The milestone tracker is not a build task and must not receive
`ready-for-agent` or direct builder assignment. After prerequisites and design
decisions are accepted, open small implementation issues with their own
scenarios and owner approval. A merged milestone spec approves direction,
not remote side effects or the entire milestone as one agent run.
